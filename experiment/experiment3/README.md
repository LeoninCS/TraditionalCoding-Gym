# Experiment 3：合并重复的并发调用

> 类型：并发函数 · 语言：Go 1.22+ · 难度：入门进阶 · 建议时长：60～90 分钟
> 规模：核心实现约 50～100 行，连同临时验证以 500 行以内为参考，不按行数验收。

实现一个简化版 Singleflight：同一个 key 正在执行时，其他同 key 调用等待并共享这次结果，避免重复计算。

这次重点练习保护共享状态，以及让多个调用等待同一份结果。

## 接口

```go
package singleflight

type Group struct {
    // 内部结构自行设计
}

func (g *Group) Do(key string, fn func() (int, error)) (int, error)
```

- `Group`：管理一组调用，`var g Group` 就能使用，使用后不要复制它。
- `key`：任务标识，区分大小写，允许空字符串，长度不超过 128 字节。
- `fn`：本次调用提供的计算函数，返回值可以是任意 `int`；返回错误时也可以带非零值。
- 最多同时存在 10,000 个 `Do` 调用。假设实际执行的 `fn` 最终会返回，且不会 panic 或调用 `runtime.Goexit`。
- 不要求处理 nil 的 `*Group`、超时、取消、永久阻塞，以及 `fn` 直接或间接调用同一个 `Group.Do` 的情况。

## 要求

1. **REQ-01 零值可用**：不需要额外初始化；空 key 和普通 key 按相同规则处理。
2. **REQ-02 参数校验**：`fn == nil` 时，在本次调用的 goroutine 中直接 panic，不约束文案。即使同 key 已有任务，也要先校验，且不能干扰已有任务。
3. **REQ-03 合并调用**：同一 `Group`、同一 key 最多有一个 `fn` 在执行。判定该 key 没有进行中的任务时，本次调用发起一轮计算；有进行中的任务时，必须加入该轮并等待结果，不执行自己提供的 `fn`。
4. **REQ-04 共享结果**：同一轮的所有调用都原样返回执行者的值和错误，包括错误伴随的非零值。必须等该轮 `fn` 返回后才能返回结果。
5. **REQ-05 相互独立**：不同 key 可以同时计算；一个 key 的 `fn` 被阻塞时，另一个 key 仍能完成。不同 `Group` 之间也不能互相影响。
6. **REQ-06 不缓存结果**：本轮结束后清理其进行中状态；后续调用重新执行自己的 `fn`，成功和失败都一样。新一轮不能改写上一轮等待者要领取的结果。

“同一轮”以调用实际参与合并的时刻为准，不按启动 goroutine 的先后判断。恰好与上一轮收尾重叠的调用，可以共享上一轮结果，也可以开启下一轮；上一轮所有 `Do` 都已返回后，再调用就必须重新计算。

## 实现约束

- **CHECK-01**：只用标准库；共享状态没有数据竞争；等待必须使用同步机制，不能忙等或用 `time.Sleep` 轮询。不得遗留永久等待的 goroutine。通过代码 Review 和竞态检测检查。
- **CHECK-02**：查找进行中的 key 应为平均 `O(1)`；一轮有 `m` 个调用时，结果分发总开销为 `O(m)`，不计 `fn`、阻塞等待和调度。及时清理完成轮次的记录，不累计保留历史 key 和结果；等待者尚未领取的结果可以暂存，不要求收缩容器的底层容量。通过源码注释和 Review 检查。

## 示例

使用同一个 `Group`，假设调用 A 已经发起 `"user:42"` 的计算，最终返回 `42, nil`：

| 操作 | 结果 |
| --- | --- |
| A 的计算尚未完成，B、C 加入同一轮 | B、C 等待，不执行各自的 `fn` |
| 此时调用 D 处理 `"user:99"` | D 可以独立执行自己的 `fn` |
| A 的 `fn` 返回 `42, nil` | A、B、C 都拿到 `42, nil`，不要求三者返回顺序 |
| A、B、C 都已返回，再调用 `"user:42"` | 重新执行新调用的 `fn` |

如果 A 返回的是 `-1, errQuery`，A、B、C 就都返回 `-1` 和同一个错误 `errQuery`。

## 验证要点

以下场景均需验证；测试只使用公开接口，临时测试文件不提交到仓库。

| 场景 | 对应要求 | 操作与期望 |
| --- | --- | --- |
| TC-01 基本调用 | REQ-01、04 | 零值 `Group` 分别处理普通 key 和空 key；正常返回 `7, nil`。另验证 `0`、负数和平台 `int` 边界值原样返回 |
| TC-02 非法回调 | REQ-02 | 空闲时传 nil 回调，必须 panic；同 key 已有阻塞任务时再传 nil，也必须直接 panic，原任务释放后仍正常返回 |
| TC-03 同 key 合并 | REQ-03、04 | 并发压力验证 + Review：多个调用处理同 key，回调返回 `42, nil`；回调执行不能重叠，结果均正确。结合 Review 确认调用会加入进行中的轮次，同轮只执行一次回调 |
| TC-04 共享错误 | REQ-03、04 | 并发压力验证 + Review：回调返回 `-1, errQuery`，调用均得到这个值和同一个预先创建的错误；结合 Review 确认等待者直接共享本轮结果 |
| TC-05 独立执行 | REQ-05 | 一个 Group 的 key A 被阻塞时，该 Group 的 key B 和另一个 Group 的 key A 都能先完成，结果各自正确 |
| TC-06 再次执行 | REQ-06 | 同 key 前次 Do 返回后再次调用，两次分别执行各自的 fn，得到各自结果；前次成功或失败都不影响再次执行 |
| TC-07 混合并发 | REQ-03～06 | 多轮混合 key 并发调用，同 key 的 fn 不重叠，不同轮和不同 key 的结果不混用；全部调用可结束，竞态检测无报告 |

并发验证用同步信号控制 `fn` 的进入和释放，每次等待加宽松超时，失败时也要释放阻塞任务。仅在调用 `Do` 前发送“已启动”信号，不能证明它已经加入某一轮；不要据此断言所有启动的 goroutine 必须共享一次计算。TC-03、04 的压力验证只检查可观察结果，合并与共享逻辑还需代码 Review；Review 不用于判定某次运行的具体调度，不用 `time.Sleep` 猜测调度。

## 文件与运行

手写实现放在 `experiment/experiment3/code/singleflight.go`，包名为 `singleflight`。只保留实现源码、README 和必要的 `go.mod`，不创建评测机或永久测试文件。

从仓库根目录初始化：

```sh
mkdir -p experiment/experiment3/code
cd experiment/experiment3/code
go mod init traditionalcoding-gym/experiment3
go mod edit -go=1.22
```

写完后，在 `code/` 中执行 `gofmt -w singleflight.go`；`gofmt -l singleflight.go` 应无输出。

编译和测试使用仓库外的临时副本。在副本中准备验证用的测试文件，再运行：

```sh
go build ./...
go test -count=1 -timeout=60s ./...
CGO_ENABLED=1 go test -race -count=1 -timeout=60s ./...
```

需要 Go 1.22+；竞态检测还需要支持 `-race` 的平台和 C 编译器。验证后清理临时文件。

完成标准：接口与上述规则一致，格式化、编译和临时验证通过，并在源码注释中简述开销、如何避免重复执行，以及一轮结束后如何让等待者拿到结果。未写实现和有效测试时，空包编译通过或 `[no test files]` 不代表完成。
