# 古法编程训练题制定规范

本文用于制定 `experiment/experimentN/README.md` 中的训练题。目标是让题目能够被独立理解、独立实现和稳定验收，同时保留方案设计与踩坑的空间。

默认约定：AI 或朋友可以帮助选题、检查题面和在完成后 Review；实现代码由练习者手写。

实验目录只保留实现源码、`README.md` 和构建所需配置（如 `go.mod`）。不创建或保留 judge、可执行测试源码、评测脚本、评测报告和编译产物。需要验证时，在仓库外的临时副本中编写测试并运行；README 可以保留场景与期望，不要求提交测试文件。下文的测试规则仅适用于临时验证。

## 1. 规则用词

题面统一使用以下约束强度，避免“最好”“合理处理”“正常工作”等无法验收的表达：

| 用词 | 含义 |
| --- | --- |
| 必须 | 基础题的通过条件，缺失或不符合即未完成 |
| 应当 | 推荐的质量要求；若作为通过条件，必须改写为“必须” |
| 可以 | 可选实现，不影响基础题验收 |
| 不要求 | 明确排除在基础题范围外，不得出现在必测项中 |
| 禁止 | 实现限制，必须说明使用静态检查还是人工 Review 验收 |

## 2. 出题原则

每道题必须满足以下原则：

1. **目标单一**：基础版本重点训练一到两个核心能力，额外能力放入加分项。
2. **范围可控**：以手写的实现代码与临时验证测试合计 500 行以内为范围目标。空行、注释和 `go.mod` 不计入；默认不把行数作为机械验收项。若某题将其设为硬限制，必须同时给出统计对象和统计命令。
3. **结果可观察**：要求描述输入、输出、状态变化或副作用，不能只描述主观质量。
4. **规则无歧义**：两个不了解出题意图的人，仅阅读题面也应得到相同的行为理解。
5. **测试可推导**：每个强制行为都能从题面直接推导出测试，不设置未公开规则的“惊喜测试”。
6. **难度来自问题本身**：不能靠缺少边界、模糊术语或猜测错误处理方式制造难度。
7. **不过度指定实现**：除非某种实现方式就是训练目标，否则只约束外部行为与复杂度。

如果基础版本无法满足上述规模目标或预计超过两小时，应拆成多个 experiment，或将次要功能移到加分项。

## 3. 每道题的必备结构

每份题目 README 必须包含以下栏目。栏目中确实不适用的维度可以省略；只有读者可能合理误解为在范围内的边界，才必须明确写“不要求”。

### 3.1 元信息

必须给出：

- 题目编号与名称；
- 类型，例如算法、数据结构、函数、命令行工具或小型项目；
- 使用语言与最低版本；Go 题应明确最低 Go 版本；
- 难度、建议完成时间和规模预算；
- 主要训练目标，但不得直接写出完整解法。

### 3.2 任务与范围

必须用一到三句话说明最终要交付什么，并分别列出：

- **目标**：基础版本必须实现的能力；
- **非目标**：容易被误认为需要实现，但本题明确不要求的内容，例如并发安全、持久化、网络访问或 UI；
- **加分项**：基础版本通过后才做的独立扩展。

基础要求和加分项不得混写。未完成加分项不能导致基础验收失败。

### 3.3 交付约定

必须固定以下信息：

- 实现目录、包名、实现源码和必要构建配置，不要求提交测试文件；
- Go module 的准确位置，不能让练习者在仓库根目录和实验目录之间自行选择；
- 编译和格式化命令，以及执行命令的工作目录；如提供测试命令，注明在仓库外的临时副本中运行；
- 依赖策略的例外；若仓库没有其他约定，默认允许标准库，禁止第三方依赖和外部服务；
- 是否需要在 README 或源码注释中补充设计说明、复杂度说明或复盘记录，不单独创建说明文件。

所有命令必须注明工作目录和工具链前置条件，且不能依赖未声明的本地文件、缓存或全局配置。发布题目时应先复核路径和命令；需要实际编译或测试时，在临时副本中完成，生成文件和验证产物不写入仓库。若题目依赖环境变量、数据文件、端口或系统工具，必须给出版本、准备方式和缺失时的预期行为。

### 3.4 公共接口或输入输出契约

库类题必须给出准确的类型、函数和方法签名；CLI 或服务类题必须给出参数、输入输出格式、退出码或协议。

接口说明必须覆盖其中适用的内容：

- 每个参数的含义、合法范围和所有权；
- 返回值、错误值和副作用；
- 输入是否允许被修改；
- 操作是否会改变内部状态，以及改变什么；
- 非法输入是返回 `error`、忽略、修正还是 `panic`；
- 零值实例、`nil`、空输入、重复输入和极值是否支持；
- 是否要求并发安全、可重入或调用顺序；
- 是否允许修改给定的公共接口。

确实不适用的维度可以省略；不准备支持或测试、但读者可能合理遇到的输入，必须明确写成“超出题目输入范围，不要求处理”，不能留给实现者猜测。

### 3.5 行为规则

所有对外可观察的基础行为必须使用 `REQ-01`、`REQ-02` 等编号逐条描述，便于与测试建立映射。每条规则只表达一个主要行为，并说明：

- 前置条件；
- 执行的操作；
- 可观察的返回值或最终状态；
- 必须发生和禁止发生的副作用。

状态型题目还必须定义初始化、成功与失败操作、重复操作、状态转换和失效规则。涉及顺序、优先级、相等判断、命中、过期等术语时，必须给出准确含义；存在多个合法结果时，必须说明任一结果均可，或给出确定的决胜规则。

### 3.6 约束与非功能要求

根据题目类型明确以下内容：

- 输入数量、数值范围、容量、数据规模和调用次数；
- 时间复杂度是平均、摊还还是最坏情况，并定义其中的 `n`；
- 空间复杂度是否包含返回结果、缓存或输入副本；
- 内存、文件、网络、时钟、并发和确定性要求；
- 禁止使用的库、容器、反射、代码生成或外部服务。

无法由黑盒测试判断的强制条件使用 `CHECK-01`、`CHECK-02` 等编号，并注明验收方式。复杂度和禁止使用某个内部组件通常必须通过“设计说明 + 代码 Review”或静态检查验收，不能仅依赖毫秒级耗时阈值。

### 3.7 示例

至少提供一个完整的正常示例。状态型题目应使用操作序列逐步给出返回值和关键状态；CLI 题应给出完整命令、标准输入、标准输出、标准错误和退出码中适用的部分。

示例必须遵守以下规则：

- 示例中的每个行为都已在正文定义；
- 示例与接口、边界和复杂度要求不冲突；
- 展示概念内部状态时，要注明它只用于解释，不代表必须提供该查询接口；
- 示例只帮助理解，不能代替正式行为规则和测试；
- 不提供关键实现代码、可直接翻译的伪代码或完整解题步骤。

### 3.8 完成条件

完成条件必须是可以明确判断的清单，至少包括：

- 项目可以编译；
- 每个“必测”场景均已验证符合题面；需要可执行测试时，在临时副本中使用有效断言验证；
- 实际运行的基础测试全部通过，且测试文件与验证产物没有留在仓库；
- 格式化检查通过；
- 公共接口与题面一致；
- 已满足实现限制；
- 能说明复杂度和关键不变量。

Go 题默认要求 `gofmt`。需要运行 `go test ./...` 时，在临时副本中准备测试并执行；并发安全要求可使用 `go test -race ./...` 验证，否则竞态检测只用于并发加分项。测试文件和编译产物不属于交付内容。

## 4. 测试用例制定规则

### 4.1 测试责任

默认由题目制定者在 README 中给出测试场景和精确期望，不要求练习者提交可执行测试。需要自动验证时，在临时副本中编写和运行测试，题面不直接附上完整测试实现。

临时验证必须满足：

- 测试覆盖题面已经声明的行为，不得增加新要求；
- 验证所需的边界必须先写入公开题面；
- 测试不得内嵌参考算法、复制生产实现或依赖私有结构。

### 4.2 需求与测试的可追溯性

每条 `REQ-*` 可观察行为必须至少对应一个 `TC-*` 测试场景。一个测试可以覆盖多条要求，但必须明确列出映射；没有对应公开要求的测试不得作为基础验收条件。`CHECK-*` 实现或非功能限制则映射到题面注明的静态检查、设计说明或代码 Review，不强行为其编造黑盒测试。

README 中至少提供如下测试矩阵：

| 测试 ID | 对应要求 | 场景与前置状态 | 输入或操作序列 | 精确期望 | 级别 |
| --- | --- | --- | --- | --- | --- |
| `TC-01` | `REQ-01` | 描述初始状态 | 描述输入 | 返回值、最终状态和副作用 | 必测 |

“精确期望”必须说明可观察的返回值、错误、最终状态以及不应发生的副作用，不能只写“执行成功”或“结果正确”。

### 4.3 最低覆盖范围

测试矩阵至少考虑以下类别，并根据题目适用性取舍：

1. **基本路径**：每个公开接口至少一个正常用例。
2. **失败路径**：未命中、拒绝、错误返回或失败后的状态。
3. **边界值**：空输入、零、一个元素、最小合法值、最大合法值及其附近。
4. **重复与更新**：重复读取、重复写入、覆盖、删除不存在项等适用行为。
5. **状态转换**：连续操作后验证中间返回值、最终状态和下一步行为。
6. **无副作用操作**：查询、失败操作或只读操作不得意外改变状态。
7. **不变量**：长期操作后仍必须成立的容量、长度、唯一性、顺序或一致性约束。
8. **实例隔离**：多个实例不能共享非预期状态。
9. **大规模或退化输入**：用于发现明显的复杂度退化，但不使用苛刻的机器耗时作为唯一判定。
10. **并发行为**：仅当题目明确要求并发安全时才是必测项。

非法输入只测试题面已经定义的处理方式。如果题面声明某类输入不会出现，测试不得自行规定其行为。

不同类型的题目还应重点覆盖：

| 题目类型 | 重点测试 |
| --- | --- |
| 纯函数或算法 | 空集、单元素、重复值、顺序、极值、输入是否被修改 |
| 有状态组件 | 初始化、连续状态转换、重复操作、失败后状态、实例隔离 |
| CLI 或文件工具 | 参数错误、退出码、stdout/stderr、临时目录、已有文件和清理行为 |
| 网络或并发组件 | 超时、取消、部分失败、竞态和资源释放；仅在题目范围内测试 |

### 4.4 单个测试的质量要求

每个测试必须：

- 使用能表达“条件与预期”的名称；
- 按 Arrange–Act–Assert 或等价结构组织；
- 优先通过公共接口进行黑盒验证；
- 验证外部行为，不读取私有字段，不绑定某一种正确的内部实现；
- 使用独立 fixture，不依赖其他测试、执行顺序或共享可变状态；
- 默认执行必须可复现，不依赖真实网络、真实时间、全局机器状态或极短超时；随机测试另按下一节处理；
- 在失败信息中显示关键步骤、输入、期望值和实际值；
- 完成资源清理，文件测试使用独立临时目录；
- 不断言契约外细节：错误优先按题面声明的类型或 `errors.Is/As` 判断，除非错误文案本身属于契约；无序结果按集合比较；多个合法结果接受任一结果；浮点误差和时间窗口必须由题面预先定义；
- 不通过跳过断言、只打印结果或只验证“不报错”来代替行为断言。

多个输入遵循同一规则时，Go 测试应当优先考虑 table-driven tests，但不要为了表驱动而把复杂状态序列塞进难以阅读的表格。

### 4.5 随机、属性和差分测试

算法或有状态题可以增加随机、属性或差分测试，但必须：

- 临时测试默认使用固定种子；若允许动态种子，必须打印种子并提供注入该种子重新运行的方法；
- 属性测试可以直接验证公开不变量；差分测试必须与一个更简单、明显正确的参考模型比较；
- 失败时打印种子和完整的可复现输入或操作序列；具备 shrink 能力时，应进一步输出缩减后的反例；
- 作为确定性示例测试的补充，不能完全替代它们。

### 4.6 性能与复杂度测试

复杂度主要通过设计说明和代码 Review 验证。规模测试只用于排除明显退化，并应为不同机器留出充分余量。

除非性能测量本身就是题目目标，否则禁止使用非常紧的 wall-clock 阈值判断通过与否。若确需 benchmark，必须固定数据规模、预热方式、统计指标和允许误差，并将环境差异写入验收说明。

### 4.7 回归与反例校验

每发现一个缺陷，都应在临时副本中补充一个能稳定复现该缺陷的测试，再修复实现。测试应有有效断言，能在缺陷仍存在时失败；不向仓库提交测试或评测文件。

## 5. 实现限制与测试的边界

以下要求不能混为一谈：

| 要求类型 | 主要验收方式 |
| --- | --- |
| 返回值、错误、状态与副作用 | 自动化黑盒测试 |
| 包名、签名、文件和命令 | 编译、脚本或静态检查 |
| 禁用某个库或指定手写组件 | 静态检查与代码 Review |
| 时间、空间复杂度 | 设计说明、代码 Review，辅以宽松规模测试 |
| 可读性、命名和职责划分 | 代码 Review |

不能为了验证实现限制而让测试读取私有字段，也不能为了测试方便给生产 API 增加与题目无关的调试方法。可以通过后续公开行为间接验证内部状态变化。

## 6. 禁止泄露答案

题目 README 只定义问题、接口和验收标准，禁止包含：

- 完整实现或关键代码片段；
- 足以直接翻译为实现的完整伪代码；
- 核心数据结构组合和逐步算法，除非它们本身就是明确的教学目标；
- 强制私有字段、哨兵结构或内部遍历方向等非必要细节；
- 在测试中内嵌参考算法、复制核心生产逻辑或检查私有结构。

如需提示，应按层级放在 README 的折叠区中，默认不展示。题目发布时，不得把参考实现放在 experiment 目录或从题面直接链接。

## 7. 发布前检查清单

发布题目前，制定者必须逐项确认：

- [ ] 题目只聚焦一到两个核心训练目标，并符合约 500 行的规模预算。
- [ ] 目录、module、包名、公共接口和执行命令均已固定。
- [ ] 所有术语、合法输入、边界、错误和副作用都有定义。
- [ ] 适用或容易引起误解的零值、空值、重复值、极值、`nil` 和并发要求均已明确支持或明确排除。
- [ ] 所有可观察基础行为都有 `REQ-*` 编号并映射到 `TC-*`；其他强制条件都有 `CHECK-*` 编号和验收方式。
- [ ] 示例、规则、测试矩阵和完成条件相互一致。
- [ ] 测试只验证公开行为，不依赖私有实现，也不包含未声明要求。
- [ ] 实现限制和复杂度使用了正确的验收方式。
- [ ] 基础要求与加分项完全分离。
- [ ] 已复核声明的工具链、路径和命令；如实际编译或测试，已在临时副本中完成，未在仓库留下测试、评测文件或编译产物。
- [ ] 题面没有泄露完整解法。

## 8. 推荐题目模板

````markdown
# Experiment N：题目名称

> 类型：... · 语言：Go ... · 难度：... · 建议时长：... · 规模：...

## 训练目标

- ...

## 题目

用一到三句话描述需要交付的结果。

## 范围

必须实现：...

不要求：...

## 交付与运行方式

- 目录与文件：...
- Module 与包名：...
- 允许或禁止的依赖：...
- 执行目录与命令：...

## API 或输入输出

给出准确签名、格式、错误和副作用约定，例如：

```go
package example

func Do(input string) (Result, error)
```

## 行为规则

- REQ-01：...
- REQ-02：...

## 输入约束

- 数据范围：...
- 并发、I/O 和环境约束：...

## 非功能要求与检查项

| 检查 ID | 强制条件 | 验收方式 |
| --- | --- | --- |
| CHECK-01 | 时间与空间复杂度：... | 设计说明 + 代码 Review |
| CHECK-02 | 禁止使用：... | 静态检查或代码 Review |

## 示例

给出完整输入、操作序列、输出与必要解释。

## 测试矩阵
````
