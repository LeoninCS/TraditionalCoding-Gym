# 评测机生成与维护提示词

本文提供一组可以直接复制使用的提示词，用于在每个实验的 `judge` 目录中生成和维护自动评测机。

评测机的职责是判断被测实现是否满足题面公开的基础要求。它不是参考答案，也不能替代复杂度分析、代码质量和实现限制等人工 Review。

## 1. 使用方式

根据当前任务选择后文的一段提示词，并替换其中的占位符：

| 占位符 | 含义 | 示例 |
| --- | --- | --- |
| `{EXPERIMENT_DIR}` | 实验目录 | `experiment/experiment1` |
| `{BUG_DESCRIPTION}` | 已知缺陷的准确描述 | `Get 未命中后错误地刷新了顺序` |
| `{REPRODUCTION}` | 可复现的输入或操作序列 | 一段 API 调用序列 |
| `{EVIDENCE}` | 日志、提交、失败输出等证据 | `go test` 的失败信息 |
| `{MISJUDGMENT}` | 误判现象 | `正确实现被判为 FAIL` |
| `{COMMAND}` | 当前复现命令 | `bash judge/run.sh` |

首次创建评测机使用“提示词一”；已有评测机需要补全时使用“提示词二”；修复实现缺陷后补回归测试使用“提示词三”；评测机发生误判时使用“提示词四”；只想运行评测、不允许改文件时使用“提示词五”。

## 2. 统一评测约定

后续所有评测机和提示词遵守本节约定。

### 2.1 判断依据

- 具体实验的 `README.md` 是行为契约，`docs/problem-make.md` 是题目与测试的制定规范。
- 只评测题面明确声明的基础要求，不把加分项、常见做法或个人偏好变成必测项。
- 题面中的每个 `REQ-*` 对应一个或多个黑盒测试 `TC-*`。
- 题面中的 `CHECK-*` 使用其声明的静态检查或人工 Review，不得伪装成行为测试。
- 旧题没有编号时，可以在 `judge/README.md` 中建立本地编号和映射，但不能改变或补充规则含义。
- 题面、示例、API 或测试矩阵存在影响判定的冲突时，必须返回评测错误，不能擅自选择一种解释。
- 当前被测实现不是正确答案。可以编译和运行它，但不能根据它的现有行为制定期望结果或放宽题面。

### 2.2 目录与文件

持久化的仓库改动默认只允许发生在目标实验的 `judge` 目录，推荐结构如下：

```text
judge/
├── run.sh          # 唯一评测入口
├── README.md       # 运行方式、覆盖矩阵和人工检查项
├── *_test.go       # 或该题所用语言的评测代码
└── testdata/       # 仅在需要固定测试数据时创建
```

不得修改被测 `code` 目录、题目 README、实验外的 module 配置或其他用户文件。为了隔离评测，可以通过 `mktemp` 在系统临时目录创建副本，但必须注册清理逻辑并在结束时删除；禁止为此 checkout、切换分支、创建 worktree 或改写 `.git`。若题面允许的 module、包名或接口布局无法被可靠识别和公平评测，应报告题面或基础设施问题，不得静默重构仓库。

`judge/README.md` 至少记录：

- 对应题面路径；
- 工具链与运行前置条件；
- 唯一运行命令；
- `REQ/TC/CHECK` 覆盖矩阵；
- 未自动评测的项目及原因。

### 2.3 唯一入口与退出码

默认从实验目录执行：

```bash
bash judge/run.sh
```

`run.sh` 必须使用以下退出码：

| 退出码 | 最终状态 | 含义 |
| --- | --- | --- |
| `0` | `PASS` | 所有可自动评测的基础要求通过 |
| `1` | `FAIL` | 交付物缺失、编译失败、测试失败或违反可自动检查的题面要求 |
| `2` | `JUDGE_ERROR` | 工具链缺失、题面冲突、评测机故障或其他无法公平判断的情况 |

stdout 的最后一个非空行必须是 `VERDICT: PASS`、`VERDICT: FAIL` 或 `VERDICT: JUDGE_ERROR`。详细诊断写入 stderr。

错误必须按责任来源分类：

- 候选代码缺失、编译失败、测试失败或执行超时属于 `FAIL`；
- judge 自身无法编译、题面允许的 module 或路径无法确定、所需工具链或隔离设施故障属于 `JUDGE_ERROR`；
- 退出码与 `VERDICT` 缺失或不一致时，评测结果无效，按 `JUDGE_ERROR` 报告。

`PASS` 只代表自动评测通过。无法自动验证的 `CHECK-*` 必须在输出和 `judge/README.md` 中标记为待人工检查，不能声称整个实现已经被完全证明正确。

### 2.4 公平性与稳定性

- 优先通过公开 API、CLI 输入输出、退出码和公开副作用进行黑盒评测。
- 不读取私有字段，不使用 `unsafe`、`linkname`、反射或源码形状推断内部状态。
- 不要求特定字段名、文件拆分、算法步骤或数据结构，除非题面明确将其列为强制项。
- 随机测试默认使用固定种子；失败时输出种子和完整可复现输入或操作序列。
- 测试之间相互隔离，不依赖执行顺序、真实网络、真实时间、缓存或用户全局配置。
- 文件测试使用独立临时目录并清理资源；不得改写候选代码。
- 不使用苛刻的 wall-clock 阈值证明复杂度；规模测试只排除明显退化。
- 只有题面要求并发安全时，才能把竞态检测作为基础通过条件。
- 对多个合法结果、无序结果、错误类型、浮点误差和时间窗口，只能按照题面约定比较。
- 若需要源码静态检查，应优先使用 Go AST 等结构化方式，避免用字符串或正则扫描造成误判。

### 2.5 安全边界

仓库中的评测机不是安全沙箱，只适合运行自己编写或可信来源的代码。评测不可信提交时，必须在仓库之外增加容器、资源限制、网络隔离和权限隔离；不能仅依靠 `run.sh` 保证安全。

## 3. 提示词一：首次生成评测机

```text
请为 `{EXPERIMENT_DIR}` 生成一个自动评测机。所有新增或修改文件只能位于
`{EXPERIMENT_DIR}/judge`，不得修改题面、候选代码、go.mod、go.work 或仓库其他文件。

开始前完整阅读：

1. `{EXPERIMENT_DIR}/README.md`
2. `docs/problem-make.md`
3. `docs/judge-make.md` 中的“统一评测约定”
4. 当前实验的 module、包名和构建配置

你是评测机作者，不是解题者。题目 README 是行为契约。候选实现只能作为被测对象，
不能作为预期结果的来源。不得根据常见做法、个人偏好或某一种实现补充要求。

先进行可评测性检查：

- 接口、输入范围、错误、边界和副作用是否足以区分对错；
- 题面允许的所有 module、包名和工作目录布局是否都能被确定识别并公平执行；
- 题面、示例和测试矩阵是否一致；
- 是否存在会影响最终结论的未定义行为。

若存在阻断公平评测的歧义，不要猜测，也不要修改题面。停止生成行为断言，列出需要
补充的题面位置，并报告 `JUDGE_ERROR` 语义。非阻断问题可以继续，但必须记录在
`judge/README.md`。

然后整理评测范围：

- 将每个可观察的 `REQ-*` 和必测 `TC-*` 映射到自动测试；
- 将 `CHECK-*` 映射到可靠的静态检查或人工 Review；
- 明确列出不评测的加分项、非目标和契约外输入；
- 旧题没有编号时，在 `judge/README.md` 中为明确规则建立本地映射，不改变其含义。

实现评测机时必须：

- 创建 `judge/run.sh` 作为唯一入口，并创建记录覆盖关系的 `judge/README.md`；
- 只通过公开接口和公开副作用进行黑盒评测；
- 仅在题面适用且已明确声明或可直接推导时，覆盖基本路径、失败路径、边界值、重复
  操作、状态转换、无副作用行为、实例隔离和不变量；
- 不测试题面明确排除的输入、加分项或未定义行为；
- 不读取私有字段，不绑定特定内部实现，不把参考算法或生产实现复制进测试；
- 对适合差分测试的问题，只使用更简单的规格模型，不复制目标算法；
- 随机测试使用固定种子，失败时打印种子和完整反例；
- 文件测试使用独立临时目录，不依赖真实网络、真实时间、测试顺序或全局状态；
- 设置宽松、可解释且不依赖额外系统工具的超时，区分候选程序超时和评测机故障；
- 源码检查只用于题面明确的 `CHECK-*`，优先使用结构化解析而非字符串匹配；
- 不用紧迫的 wall-clock 阈值证明时间复杂度。

统一入口从实验目录执行：

    bash judge/run.sh

退出码必须为：0 表示 PASS；1 表示候选实现 FAIL；2 表示 JUDGE_ERROR。stdout 最后一个
非空行必须是对应的 `VERDICT: ...`；详细失败信息写入 stderr，并包含测试名称、对应
要求、关键输入或操作序列、期望值和实际值。

完成后：

1. 格式化评测代码；
2. 运行评测机自身的测试或静态检查；
3. 实际执行统一入口；若候选代码尚未完成，正确得到 FAIL 可以作为入口验证结果，
   但不能伪称候选实现已通过；
4. 若已有经过独立确认的合规实现，可在系统临时目录中验证兼容性；不得为此生成或
   持久化完整参考实现，也不得把样例实现当作期望结果来源。可以用最小故意错误样例
   检查测试敏感性，但它不能代替题面覆盖分析。无法完成时如实记录未验证项。

最终报告：创建的文件、覆盖矩阵、未自动评测项、唯一运行命令、退出码契约和实际
验证结果。不得在评测文件或报告中给出题目的完整解法。
```

## 4. 提示词二：审计并补强已有评测机

```text
请审计并在有充分题面依据时补强 `{EXPERIMENT_DIR}/judge`。修改范围仅限该 judge
目录，不得修改候选代码、题面或 module 配置。

完整阅读 `{EXPERIMENT_DIR}/README.md`、`docs/problem-make.md`、
`docs/judge-make.md` 的统一约定、现有评测代码及运行说明。不要假设已有断言正确，
也不要把当前候选实现当作答案标准。

逐项完成：

1. 建立“题面要求 → 测试或检查 → 具体断言”的追踪矩阵。
2. 找出遗漏的基础要求、边界、状态转换、失败后状态和无副作用行为。
3. 找出没有题面依据的断言、对加分项的误测和对内部实现的耦合。
4. 检查多个合法输出是否被错误限制为单一输出。
5. 检查错误比较、无序集合、空值、随机种子、临时文件、全局状态和测试顺序。
6. 检查工作目录、module、工具链、超时、stdout/stderr 和退出码是否可复现。
7. 从公开规则推导常见错误实现，并确认测试能否识别；只能加入题面可推导的反例。
8. 区分黑盒行为、静态检查和人工 Review，不用耗时阈值冒充复杂度证明。
9. 确认 `PASS` 没有掩盖仍待人工检查的 `CHECK-*`。

发现题面歧义时，不得通过调整断言自行决定答案。只有影响基础判定或现有断言的歧义
才归为 JUDGE_ERROR；与当前基础评测无关的歧义只记录且不评测。发现无题面依据或
过度严格的断言时，应删除或放宽，并记录理由。

修改后运行评测机自检和 `bash judge/run.sh`。保持退出码 0=PASS、1=FAIL、
2=JUDGE_ERROR，以及 stdout 最后一行的 `VERDICT: ...` 契约。

最后报告新增、删除或放宽了哪些检查，每项引用对应题面规则；另列出仍无法自动评测
的项目及原因。不得为了提高覆盖率而添加未公开要求。
```

## 5. 提示词三：针对已知缺陷增加回归测试

```text
请根据下面的缺陷，为 `{EXPERIMENT_DIR}/judge` 增加最小、稳定的回归测试。修改范围
仅限 judge 目录。

缺陷描述：`{BUG_DESCRIPTION}`
已有复现步骤或输入：`{REPRODUCTION}`
相关提交、日志或失败输出：`{EVIDENCE}`

修改前先确认预期行为能从题面中的某个 `REQ-*`、`TC-*` 或明确文字直接推出。如果
缺陷实际暴露的是题面未定义或相互冲突的行为，不得自行规定答案，也不得修改评测机
迎合某个实现；请指出需要补充题面的具体位置，本次回归测试任务以“无法公平加入，
JUDGE_ERROR”结束。只有该歧义同时影响现有基础评测结论时，才调整运行时 verdict。

若题面依据充分：

- 将复现缩减为只包含触发缺陷所需的最少公开操作；
- 新增名称明确的回归测试，标注对应要求和缺陷描述；
- 同时断言返回值、最终可观察状态及题面规定的无副作用；
- 只使用公开接口，不读取私有字段，不固定某一种内部实现；
- 使用固定数据和固定种子，失败信息足以直接复现；
- 确保测试不依赖执行顺序、机器速度、真实时间、网络或用户环境；
- 确认没有误测加分项或契约外输入。

如果缺陷版本与修复版本都可获得，请分别执行，证明该测试在缺陷版本失败、在修复
版本通过；只能使用系统临时目录中的副本或用户已提供的独立版本。不得 checkout、切换
分支、创建 worktree 或改写当前候选代码。若无法获得其中一个版本，明确记录尚未完成
的红绿验证，不得伪称已验证。

最后运行 `bash judge/run.sh`，报告测试名称、题面依据、最小反例、红绿验证结果和
统一入口的退出码行为。
```

## 6. 提示词四：调查并修复评测机误判

```text
请调查并修复 `{EXPERIMENT_DIR}/judge` 的误判。修改范围仅限 judge 目录。

误判现象：`{MISJUDGMENT}`
被评实现及证据：`{EVIDENCE}`
复现命令：`{COMMAND}`

先在题面声明的工作目录和工具链下原样复现，记录命令、退出码、stdout、stderr、随机
种子和关键环境。然后将问题归为以下一种：

- 假阴性：符合题面的实现被判为 FAIL；
- 假阳性：违反题面的实现被判为 PASS；
- 基础设施错误：路径、module、工具链、超时或评测机自身故障；
- 题面歧义：现有契约不足以区分对错。

对每个相关断言追溯到题面原文：

- 没有题面依据时，删除或放宽该断言；
- 题面允许多个结果时，改为接受所有合法结果；
- 比较方式错误时，按契约修正集合、错误类型、浮点或副作用比较；
- 错误实现漏检时，增加最小且能从题面推导的反例；
- 环境故障时，修复隔离、路径、清理或错误分类，不把它记为候选失败；
- 题面存在歧义时，不擅自选择解释，返回 JUDGE_ERROR，并提出最小题面修订建议。

不得因为当前实现看起来合理就放宽契约，也不得为了抓住某个错误实现而检查私有字段、
源码形状或特定算法。修复后既要重跑误判复现，也要运行完整评测，确认没有破坏其他
`REQ/TC` 覆盖。

最后报告误判类型、根因、题面依据、修改内容、复现前后结果和统一入口的实际退出码。
```

## 7. 提示词五：只运行评测并给出结论

```text
请只运行 `{EXPERIMENT_DIR}` 的现有评测机并报告结论，不得修改仓库中的任何文件，也
不得修复候选实现或评测代码。允许工具链缓存以及系统临时目录中的必要写入，但必须
清理评测创建的临时资源。

先阅读 `{EXPERIMENT_DIR}/README.md`、`{EXPERIMENT_DIR}/judge/README.md`、
`{EXPERIMENT_DIR}/judge/run.sh`、它调用的脚本，以及 `docs/judge-make.md` 的统一评测
约定。若 runner 会持久修改仓库，停止执行并报告 JUDGE_ERROR；若能在系统临时副本中
无副作用地运行，可以改用临时副本并明确报告。然后从实验目录执行：

    bash judge/run.sh

记录退出码、stdout 最后一条 VERDICT、stderr 中的失败信息和所有待人工检查项。按以下
规则给出结论：0=PASS，1=FAIL，2=JUDGE_ERROR。命令输出与退出码不一致时，以
JUDGE_ERROR 报告，不要自行猜测候选实现是否正确。

最终只报告：评测结论、失败的 `TC/REQ`、待人工检查的 `CHECK`、复现命令，以及判断
受限于哪些题面或环境问题。不得依据当前实现补充评测规则。
```

## 8. 评测机发布检查清单

生成或修改评测机后，逐项确认：

- [ ] 只修改了目标实验的 `judge` 目录。
- [ ] 唯一入口是从实验目录执行 `bash judge/run.sh`。
- [ ] 退出码和最后一行 `VERDICT` 保持一致。
- [ ] 每个自动测试都能追溯到公开题面要求。
- [ ] 每个可观察的基础要求都有测试，未自动检查项已说明原因。
- [ ] 未评测加分项、非目标、未定义输入或私有实现。
- [ ] 测试可重复、相互隔离，并包含有效断言和可复现失败信息。
- [ ] 编译错误、候选失败和评测基础设施错误能够正确区分。
- [ ] 没有用紧迫耗时阈值代替复杂度分析。
